## 🎨 طراحی منو

### تصمیم طراحی: حذف حس «پاپ‌آپ»

در نسخهٔ اولیه، منوی اصلی از کلاس `.overlay` (که برای دیالوگ‌های شناور طراحی شده بود) ارث‌بری می‌کرد — شامل `backdrop-filter: blur`، کارت متمرکز با `border` و `box-shadow`، و انیمیشن ورودی `scale + translateY` (انیمیشن استاندارد modal/popup). نتیجهٔ این ترکیب این بود که منوی اصلی حس «دیالوگی که روی چیزی نشسته» می‌داد، نه حس «صفحهٔ اصلی بازی».

در نسخهٔ نهایی، منو به یک **صفحهٔ تمام‌صفحه (full-bleed)** بازطراحی شد:

|ویژگی نسخهٔ قدیمی (پاپ‌آپ)|ویژگی نسخهٔ نهایی (full-bleed)|
|-|-|
|`position: fixed` + `backdrop-filter: blur`|`position: fixed` + `background: transparent` (بدون blur)|
|کارت متمرکز با `border` + `box-shadow` + `border-radius`|بدون کارت، محتوا با چیدمان ستونی توزیع شده|
|`max-width: 380px` (نوار باریک وسط)|`width: 100%` (تمام عرض)|
|انیمیشن ورودی: `scale(0.96) → scale(1)`|انیمیشن ورودی: `slide-up + fade` با staggered delay|
|حس: «دیالوگ روی صفحه»|حس: «خود صفحه»|

### ساختار منوی نهایی

منو به چهار بخش عمودی تقسیم شده:

```
┌─────────────────────────────┐
│  🐞 Bug Squasher            │ ← Brand Header
│  قبل از کرش‌کردن کدت...      │
├─────────────────────────────┤
│  \[بازیکن] \[رکورد] \[رتبه]     │ ← HUD Cards (نام/امتیاز/رتبه)
├─────────────────────────────┤
│         🕸️                  │
│         🕷️                  │ ← Spider Stage (عنکبوت روی تار)
│                             │
├─────────────────────────────┤

│  \[▶ شروع بازی           ]  │ ← Primary CTA (56px)
│  (📖)  (🏆)  (⚙️)           │ ← Secondary Icons (48px)

│  v1.0.0                     │
└─────────────────────────────┘
```

### کفش‌دوزک منو → عنکبوت روی تار

در نسخهٔ اولیه، لوگوی کفش‌دوزک 🐞 در گوشهٔ منو به‌صورت ثابت نمایش داده می‌شد. در بازطراحی، این المان با یک **عنکبوت زنده روی تار** جایگزین شد:

* **تار عنکبوت:** SVG ثابت در گوشهٔ چپ-بالای صفحه
* **عنکبوت:** المان متحرک با فیزیک گرانش (سقوط → مکث → صعود → تکرار)
* **لرزش خزیدن:** چرخش بدن عنکبوت هنگام صعود (`±4deg` با `sin(t/80)`) حس حرکت پا می‌دهد
* **فیدبک لمسی:** با لمس عنکبوت، افکت squash + ۸ ذرهٔ رنگی + ویبره رخ می‌دهد — یک **پیش‌نمایش مکانیک اصلی بازی** بدون نیاز به راهنما
* **جایگاه ثابت:** عنکبوت درون یک بلوک `spider-stage` با ارتفاع ثابت `120px` قرار دارد (نه وابسته به فضای خالی انعطاف‌پذیر)، تا روی صفحات کوتاه هم با دکمه‌ها همپوشانی نداشته باشد

### کارت‌های HUD

سه کارت آمار به منو اضافه شد:

|کارت|محتوای نمایش داده‌شده|منبع داده|
|-|-|-|
|**بازیکن**|نام بازیکن (از `localStorage`)|`playerName`|
|**رکورد**|بالاترین امتیاز (از `localStorage` + Supabase)|`highScore`|
|**رتبه**|رتبهٔ فعلی بازیکن بر اساس رکورد|`currentRank(highScore)`|

> این کارت‌ا با تابع `updateMenuHUD()` در `game.js` همگام می‌شوند.

### نوارهای ماتریکسی (بارش ۰/۱)

در نسخهٔ اولیه، بارش ۰/۱ روی کل صفحهٔ منو فعال بود و از پشت متن/دکمه‌ها رد می‌شد — خوانایی را خراب می‌کرد. در نسخهٔ نهایی:

* بارش ۰/۱ به **دو نوار عمودی ۶۰px** در لبهٔ چپ و راست صفحه محدود شد
* مرکز صفحه کاملاً ساکن و تمیز است
* عنکبوت تنها عنصر متحرک مرکز صفحه است — توجه چشم بازیکن به‌طور خودآگاه به سمت آن جلب می‌شود
* نوارها در زمان گیم‌پلی خودکار متوقف می‌شوند (با poll سبک `500ms`) — صرفه‌جویی CPU

### انیمیشن ورودی Staggered

هر چهار بخش منو با تأخیر پلکانی وارد می‌شوند:

```
Section 1 → 0.05s delay
Section 2 → 0.12s delay
Section 3 → 0.19s delay
Section 4 → 0.26s delay
```

این انیمیشن با `prefers-reduced-motion: reduce` غیرفعال می‌شود.

## 🕹️ نوار کنترل گیم‌پلی

### قابلیت جدید: پاز/بازگشت/خروج در وسط بازی

نسخهٔ اولیه هیچ راهی برای مکث یا خروج در وسط بازی نداشت — بازیکن یا بازی رو کامل می‌کرد یا اپ رو می‌بست. در نسخهٔ نهایی، یک نوار کنترل دائمی در پایین صفحهٔ گیم‌پلی اضافه شد:

|دکمه|آیکون|عملکرد|
|-|-|-|
|**مکث**|⏸️|بازی را متوقف می‌کند و دیالوگ «بازی مکث شده» را نمایش می‌دهد|
|**بازگشت به منو**|←|دیالوگ تأیید نمایش می‌دهد («پیشرفت این دور از دست می‌ره»)|
|**خروج**|⬆️|دیالوگ تأیید خروج از اپ را نمایش می‌دهد|

### ویژگی‌های نوار کنترل

* **موقعیت:** `fixed` در پایین صفحه با `safe-area-inset-bottom`
* **اندازه لمسی:** هر دکمه `48×48px` دایره‌ای — مطابق با دستورالعمل‌های دسترسی‌پذیری اندروید
* **کپشن:** هر دکمه با لمس، یک tooltip کوتاه بالای خود نمایش می‌دهد (با تأخیر `1.5s`)
* **جلوگیری از خروج ناگهانی:** بازگشت به منو و خروج، هر دو دیالوگ تأیید دارند
* **پس‌زمینهٔ گرادینت:** از پایین صفحه محو می‌شود تا با صحنهٔ بازی هماهنگ باشد

### مکث و Resume

```
مکث → freezeGame() → running = false
Resume → resumeGame() → running = true → requestAnimationFrame(update)
```

## 🔒 مبهم‌سازی کد (Obfuscation)

### چرا انجام شد

درخواست مستقیم سرپرست پروژه بود که منطق بازی (به‌ویژه الگوریتم تولید باگ‌ها، محاسبهٔ امتیاز، و ارتباط با Supabase) در نسخهٔ production مبهم‌سازی شود. اهداف:

1. **افزایش هزینهٔ مهندسی معکوس:** جلوگیری از کپی‌کردن سریع مکانیک‌ها توسط بازی‌های مشابه
2. **پنهان کردن کلید Supabase:** هرچند `anon key` ذاتاً public است، مبهم‌سازی پیدا کردن آن را در کد سخت‌تر می‌کند
3. **حفاظت از منطق گیم‌پلی:** سیستم رتبه‌بندی، فرمول‌های سرعت، و thresholds تولید باگ

### ابزار و فرآیند

|مورد|جزئیات|
|-|-|
|ابزار|[javascript-obfuscator](https://github.com/javascript-obfuscator/javascript-obfuscator)|
|فایل ورودی|`www/game.js`|
|فایل خروجی|`www/game.obf.js`|
|جایگزینی در Build|`index.html` در زمان Build به‌جای `game.js` به `game.obf.js` ارجاع می‌دهد|

### تنظیمات استفاده‌شده

* **Control Flow Flattening:** فعال — ساختار کنترلی را مسطح می‌کند
* **String Array Encoding:** فعال — رشته‌ها در آرایه‌ای رمزگذاری‌شده ذخیره می‌شوند
* **Dead Code Injection:** غیرفعال — برای حفظ حجم فایل (بازی موبایل)
* **Reserved Names:** نام‌های عمومی API (`supabase`, `localStorage`, `navigator`) مستثنی شده‌اند

### ⚠️ نکتهٔ مهم: مبهم‌سازی جایگزین امنیت سمت سرور نیست

این نکتهٔ فنی حیاتی است که در مستندات هم ثبت می‌شود:

> \*\*مبهم‌سازی فقط یک لایهٔ اضافی است.\*\* هر فردی با زمان و تلاش کافی می‌تواند کد مبهم‌شده را بازگرداند. این کار هزینهٔ مهندسی معکوس را بالا می‌برد، اما آن را غیرممکن نمی‌کند.
>
> \*\*امنیت واقعی بازی در سمت سرور نهفته است\*\* — نه در کد کلاینت:
> - امتیازها از طریق تابع `SECURITY DEFINER` در PostgreSQL نوشته می‌شوند (نه مستقیم از کلاینت)
> - RLS روی جدول `leaderboard` اجازهٔ نوشتن مستقیم را نمی‌دهد
> - اعتبارسنجی نام و امتیاز در سطح سرور انجام می‌شود
>
> اگر این لایه‌های سمت سرور نبودند، مبهم‌سازی کد هیچ ارزش امنیتی واقعی‌ای نداشت — فقط زمان کشف شدن حمله را اندکی به‌تأخیر می‌انداخت.

## 📶 سازگاری با WebView قدیمی/گوشی‌های مختلف

### مشکل کشف‌شده

بازی روی گوشی سازنده کار می‌کرد، ولی روی اکثر گوشی‌های دیگه چندتا مشکل همزمان داشت: جدول امتیازات باز نمی‌شد و اسم/امتیاز ذخیره نمی‌شد، فونت درست نمایش داده نمی‌شد، و دکمهٔ خروج رفتار متفاوتی داشت.

### علت ریشه‌ای

دو وابستگی خارجی (CDN) در نسخهٔ اولیه:

|CDN|مورد استفاده|مشکل|
|-|-|-|
|`cdn.jsdelivr.net`|کتابخونهٔ Supabase|روی شبکه‌های داخل ایران فیلتر/ناپایدار|
|`fonts.googleapis.com`|فونت‌ها|روی شبکه‌های داخل ایران فیلتر/ناپایدار|

این آدرس‌ها روی خیلی از شبکه‌های داخل ایران فیلتر/ناپایدار هستند، برای همین فقط روی گوشی‌ای که دسترسی بهتری به این سرورها داشت (گوشی سازنده) درست کار می‌کرد.

بعد از رفع این بخش، یک لایهٔ مشکل عمیق‌تر هم پیدا شد: کتابخونهٔ Supabase (نسخهٔ npm) از سینتکس نسبتاً جدید جاوااسکریپت مثل **Optional Chaining** (`?.`) استفاده می‌کند — سینتکسی که فقط از Chrome ۸۰ به بعد (تقریباً از سال ۲۰۲۰) پشتیبانی می‌شود. روی گوشی‌هایی که WebView داخلی‌شان (که اپ Capacitor داخلش اجرا می‌شود) آپدیت نشده، این خطا در سطح parse رخ می‌دهد و کل فایل کتابخونه رد می‌شود — نه فقط بخشی از آن.

### راه‌حل پیاده‌شده

1. **جاسازی محلی:** کتابخونهٔ Supabase و فونت‌ها به‌جای بارگذاری از CDN، مستقیم داخل `www/` قرار گرفتند (`supabase.min.js`, `fonts/\*.woff2`) — دیگر هیچ وابستگی شبکه‌ای برای این بخش‌ها وجود ندارد.
2. **ترنس‌پایل با Babel:** فایل کتابخونهٔ Supabase با `@babel/preset-env` (هدف: سازگاری با Chrome ۴۹ به بالا، یعنی عملاً همهٔ نسخه‌های اندروید رایج) بازنویسی شد تا از سینتکس قدیمی‌تر و سازگار استفاده کند.
3. **پیام خطای تشخیصی:** در صورت شکست اتصال به سرور امتیازات، به‌جای پیام مبهم قدیمی، دلیل دقیق فنی خطا هم زیر پیام فارسی نمایش داده می‌شود — برای تشخیص سریع‌تر مشکلات مشابه در آینده.

## 🔒 امنیت جدول امتیازات (Leaderboard)

### مشکل کشف‌شده

نسخهٔ اولیه، امتیاز رو مستقیماً از سمت کلاینت (مرورگر/اپ) با `upsert` روی جدول Supabase می‌نوشت. چون کلید `anon` به‌ناچار داخل کد کلاینت قابل مشاهده‌ست، هرکسی می‌تونست با DevTools مستقیم به جدول بنویسه و امتیاز دلخواه ثبت کنه. این دقیقاً همون اتفاقی بود که افتاد: یک ردیف فیک با امتیاز ۹۹۹۹ در صدر جدول ثبت شد.

### راه‌حل پیاده‌شده

معماری نوشتن داده از حالت *کلاینت مستقیم به جدول می‌نویسد* به حالت *کلاینت فقط یک تابع سرور را صدا می‌زند* تغییر کرد:

1. **Row Level Security (RLS):** روی جدول `leaderboard`، تمام Policyهای INSERT/UPDATE مستقیم حذف شدند. تنها Policy باقی‌مانده اجازهٔ **خواندن (SELECT)** عمومی است.
2. **تابع سرور (`submit\_score`):** یک تابع PostgreSQL با ویژگی `SECURITY DEFINER` ساخته شد که:

   * نام و طول آن را اعتبارسنجی می‌کند
   * امتیاز ارسالی را در بازهٔ منطقی (حداکثر ۲۰۰۰) چک می‌کند
   * رکورد قبلی بازیکن را با `greatest()` مقایسه و در صورت لزوم به‌روزرسانی می‌کند
   * این تابع تنها راه نوشتن روی جدول است.
3. **کد کلاینت:** تابع `syncPlayerStats` در `game.js` از فراخوانی مستقیم `db.from('leaderboard').upsert(...)` به `db.rpc('submit\_score', {...})` تغییر کرد.
4. **تست نفوذ:** با شبیه‌سازی نقش `anon` (`set role anon;`) تلاش برای نوشتن مستقیم روی جدول انجام شد و با خطای RLS (`new row violates row-level security policy`) رد شد — یعنی مسیر حمله‌ای که قبلاً استفاده شده بود، الان کاملاً بسته است.

## ⚡ بهینه‌سازی فریم‌ریت

### هماهنگ‌سازی حرکت با `dt` (دلتا-تایم)

در نسخهٔ اولیه، حرکت باگ‌ها و انیمیشن‌ها با فرض فریم‌ریت ثابت `60fps` محاسبه می‌شدند:

```js
// ❌ نسخهٔ قدیمی — فرض 60fps ثابت
b.y += speed; // speed = pixels per frame
```

این روی دستگاه‌هایی با فریم‌ریت متفاوت (مثلاً ۹۰Hz یا ۱۲۰Hz) باعث **تندتر شدن غیرمنطقی بازی** می‌شد — باگ‌ها سریع‌تر می‌افتادند، بازی ناعادلانه‌تر و غیرقابل‌پیش‌بینی می‌شد.

### راه‌حل پیاده‌شده

همهٔ محاسبات حرکت به **دلتا-تایم** تغییر کردند:

```js
// ✅ نسخهٔ نهایی — هماهنگ با dt
const dt = Math.min(time - lastTime, 50);  // cap at 50ms
lastTime = time;
const speed = (0.9 + baseSpeed) \* (dt / 16.6);  // 16.6ms = 60fps reference
b.y += speed \* b.speedMult;
```

### جزئیات فنی

|پارامتر|مقدار|توضیح|
|-|-|-|
|`dt` cap|`50ms`|جلوگیری از پرش بزرگ در صورت توقف موقت فریم (مثلاً تب‌سوئیچ)|
|مرجع فریم|`16.6ms`|معادل `60fps` — سرعت بازی روی این اساس نرمال‌سازی می‌شود|
|`typeWobble`|`dt / 250`|انیمیشن تایپ‌کردن برنامه‌نویس|
|`codeOffset`|`dt / 16`|اسکرول gutter خط‌شماره|
|`spawnTimer`|`+= dt`|زمان‌بندی تولید باگ|
|`spawnInterval`|`1400ms → 420ms`|با امتیاز کاهش می‌یابد|

### تست روی دستگاه‌های مختلف

|دستگاه|فریم‌ریت|نتیجه|
|-|-|-|
|گوشی میان‌رده (۶۰Hz)|60fps|بازی با سرعت مرجع اجرا می‌شود|
|گوشی پرچمدار (۱۲۰Hz)|120fps|بازی با همان سرعت مرجع اجرا می‌شود (نه دو برابر)|
|شبیه‌ساز با افت فریم|متغیر|به‌لطف cap `50ms`، باگ‌ها ناگهان پرش نمی‌کنند|

> این مسئله به‌خاطر طیف وسیعی از گوشی‌های کافه‌بازار (از میان‌رده تا پرچمدار با صفحه‌نمایش ۱۲۰/۱۴۴Hz) حیاتی بود.

## 🚀 راه‌اندازی و Build محلی

### پیش‌نیازها

* **Node.js** + npm
* **Android Studio** + Android SDK
* **JDK 17**

### مراحل

```bash
# نصب وابستگی‌ها
npm install

# سینک کردن تغییرات www/ با پروژهٔ اندروید
npx cap sync android

# باز کردن پروژه در Android Studio
npx cap open android
```

### مبهم‌سازی کد (پیش از Build)

```bash
# نصب ابزار
npm install --save-dev javascript-obfuscator

# تولید نسخهٔ مبهم‌شده
npx javascript-obfuscator www/game.js --output www/game.obf.js \\
  --compact true \\
  --control-flow-flattening true \\
  --string-array true \\
  --string-array-encoding rc4 \\
  --reserved-names supabase,localStorage,navigator
```

> \*\*نکته:\*\* اسکریپت `npm run obfuscate` این کار را خودکار انجام می‌دهد.

### گرفتن نسخهٔ Release (از طریق ترمینال)

```bash
cd android

# نسخهٔ AAB — برای آپلود روی کافه‌بازار
./gradlew bundleRelease

# نسخهٔ APK — برای نصب مستقیم و تست
./gradlew assembleRelease
```

خروجی‌ها:

* **AAB:** `android/app/build/outputs/bundle/release/app-release.aab`
* **APK:** `android/app/build/outputs/apk/release/app-release.apk`

### ساخت آیکون از روی لوگو

```bash
npx capacitor-assets generate --android
npx cap sync android
```

## 🚪 خروج از اپ (Exit Button)

نسخهٔ اولیه برای بستن اپ به `window.close()` و بریج‌های سفارشی غیرموجود متکی بود که رفتارش گوشی‌به‌گوشی فرق می‌کرد. با استفاده از پلاگین رسمی `@capacitor/app` (که مستقیم از بریج native خود Capacitor استفاده می‌کند، نه از قابلیت‌های محدود مرورگر)، این رفتار روی همهٔ گوشی‌ها یکسان و قابل‌اعتماد شد.

|روش خروج|مسیر|تأیید|

## ⚠️ نکات امنیتی برای توسعهٔ آینده

* فایل‌های `\*.jks` و `keystore.properties` **هرگز** نباید public/commit بشن (در `.gitignore` قرار دارند). گم‌شدن کلید امضا یعنی امکان انتشار آپدیت روی همون اپلیکیشن از بین می‌ره.
* هرگونه ستون یا جدول جدید در Supabase که کلاینت بهش دسترسی نوشتن داره، باید همین الگو (RLS محدود + تابع RPC اعتبارسنج) رو رعایت کنه؛ نوشتن مستقیم از کلاینت به‌طور پیش‌فرض ناامنه.
* مبهم‌سازی کد فقط یک لایهٔ اضافی است — امنیت واقعی همیشه باید در سمت سرور پیاده‌سازی بشه.
* کلید `anon` Supabase به‌طور ذاتی public است؛ اما کلید `service\_role` **هرگز** نباید در کد کلاینت قرار بگیره.
